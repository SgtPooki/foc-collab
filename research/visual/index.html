FOC Capability Ladder

What kinds of applications the platform can power today, what one round of tooling work adds, and what the platform features after that make possible. Every claim below was verified against the shipped contracts and SDK; the engineering detail lives in research/ in this repo.

TIER 1 · BUILDABLE TODAY

Shared applications with no servers at all

FOC storage plus the new per-data-set access rules (shipped to calibration, mainnet release in progress) already support applications where the storage network is the entire backend: no app server, no database, no host to keep running.

Functionality available now

Shared state any browser can read and replay identically Anyone can fund a thing's storage, with attributed on-chain receipts Write rules enforced by contract (allowlists, rate limits, roles) Deletion and shutdown vetoed until a chosen date CDN-speed public reads

Examples

  • A shared thing that lives only while people pay to keep it alive Its health bar is its real storage funding; every feeding is a payment anyone can verify. This is the mascot idea from standup: if the community stops funding it, it visibly declines, and the protocol gives a roughly 30-day window before the data is at risk.
  • Turn-based multiplayer between any browsers on Earth Already live: we have a working two-player game on calibration where every move is a signed record and both players' browsers compute the same board. Moves take 30 to 60 seconds to land, which suits turn-based play.
  • Multi-step handoffs with signed receipts at every step Work passes between people or AI agents; each step is signed, ordered, and independently verifiable. Today this works among participants we set up ourselves.
  • Records locked against deletion until a chosen year An access-rule contract can refuse both deletion and shutdown until a set date. At current pricing, about $1,000 keeps a terabyte provably funded for roughly 16 years, and anyone can check the balance.
TIER 2 · ONE ROUND OF TOOLING AWAY

Open participation: strangers join from a link

The contracts already permit public, rule-governed writing. What is missing is tooling: the SDK has no ergonomic path to the new access rules, and there is no way to search or filter stored records without downloading everything. Close those two gaps and applications stop being invite-only.

Functionality this adds

Anyone with the link can contribute, under contract-enforced rules Content that is searchable and filterable at consumer scale Live activity feeds instead of polling Embeddable views for any website

What that looks like

  • Public collaborative artifacts A shared canvas, board, or timeline the whole internet can write to, one contribution per person per time window, with the rule enforced by contract rather than by a moderator watching.
  • Event experiences gated by attendance Check in at a conference and your badge lets you contribute to a collective artifact that is stored permanently afterward. Part of the ticket price can fund that storage for decades.
  • Comments and guest notes on any published page The original idea this work started from: viewers of a static page leave notes that persist, with no comment server anywhere.
  • Community-curated media queues Shared playlists and reading lists anyone can add to, with the catalog of allowed entries enforced by contract.
What has to be built
  • SDK support for the new access-rule contracts (synapse-sdk; today the capability is contract-only)
  • Indexed reads: list and filter records by their labels without downloading everything (SDK front-end for events that indexers already capture)
  • Restore the sponsored-writes example contract (merged in August, reverted only for release timing)
TIER 3 · PLATFORM FEATURES AFTER THAT

Economies inside the applications, at consumer scale

With tier 2 in place, three platform features turn these applications from demos into products: payment hooks, passkey sign-in, and cheaper crowd writes. Each one also upgrades everything in tiers 1 and 2.

Functionality this adds

Paid actions: entry fees, upgrades, bounties, auctions Sign in with a passkey, no wallet or crypto knowledge Thousands of simultaneous contributors at around a third of a cent per action AI agents that pay and get paid without a human in the loop

What that looks like

  • Applications that fund their own storage Entry fees and upgrades flow back to the account paying the storage bill. The app pays for itself; the operator never holds user funds.
  • Work marketplaces with built-in escrow Payment for a step releases when the next participant accepts the work, with a protocol fee taken natively. The payment rails shipped with FOC already support this shape; it needs a hardened reference contract, not new protocol.
  • Consumer-scale participation Contract-enforced write rules currently cost about a cent per contribution because each one is its own transaction. Batching independently signed contributions cuts that to roughly a third of a cent and removes the throughput ceiling.
  • Compliance-grade record keeping as a product The deletion-veto pattern from tier 1, packaged so a buyer audits a product instead of a bespoke contract: pay once, retain provably for N years.
What has to be built
  • Charge-the-writer payment hooks and a reference escrow contract (filecoin-pay + filecoin-services)
  • Passkey signature support proven on-chain (the access-rule design already anticipates it; the gas cost needs measuring)
  • Batched writes carrying many individual signatures in one transaction (filecoin-services)
  • Let delegated agent keys make payments (today only the owner wallet can; blocks autonomous agent economies)
The compounding effect: each tier upgrades the ones before it. The mascot gains adoption fees and cosmetics people buy. The public canvas gains paid features and event-scale crowds. The signed-handoff pipeline gains escrowed payment per step and agents that participate on their own, which is the story our agent go-to-market needs: verifiable multi-party work where no participant has to run or trust a coordinator.
